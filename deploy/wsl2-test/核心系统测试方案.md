## 1. 测试概述与目标

### 1.1 测试目标
对 VeroRun 官方版核心系统执行一次**全面功能 + 回归验证**，达成：
1. 验证核心系统在 WSL2 官方版部署下的功能完整性、正确性
2. 验证**鉴权与会话安全链路**（登录/登出/刷新/权限隔离/审计）
3. 验证**后台管理全模块**增删改查、状态流转、数据一致性
4. 验证**订阅计费/配额/域名**等系统级能力的正确性
5. 暴露部署环境特有的兼容性/稳定性问题
6. 为版本发布提供质量依据（准入/准出）

### 1.2 测试对象架构（服务拓扑）

nginx 统一入口（80/443，含 HTTP→HTTPS 与安全加固），按路径前缀分发到 4 个 gunicorn 服务 + 守护进程：

```
                        ┌─────────────────────────────┐
   用户/管理员/Agent      │   nginx (80/443, 自签证书)     │
   ────────────────────► │   安全基线 M1-M17 加固          │
                        └───────┬──────────┬──────────┘
        /admin/*                 │          │  /auth/*,/subscribe,/user-*?
        │  ┌──────────────┐   ┌──┴─────┐  ┌─┴────────────────┐
        └─►│ verorun-admin│◄─►│auth-ctr│◄►│ verorun-main      │
           │  (8084 壳+登录)│   │(8083)   │  │ (8081 前台/用户/API)│
           └──────────────┘   └────────┘  └──────────────────┘
                                   ▲   ┌──────────────────────┐
                                   └───┤ verorun-health(8085)  │
                                       │ verorun-guardian(守护)│
                                       └──────────────────────┘
   后端共同依赖： PostgreSQL appdb（126 张业务表，含 public 业务表）·
                /auth、/admin 的限流 rate=10r/s · WebSocket /ws,/socket.io
```

### 1.3 关键架构事实（影响测试设计）
1. **auth-center(8083) 承载绝大多数业务**（用户/CMS/系统管理/评论/Agent 底座），main_site(8081) 承载前台展示 + 用户控制台页面 + 少量 API
2. **admin(8084) 是后台外壳 + 登录鉴权 + 主题管理**，后端业务 API 大量经 `/admin/*` 由 auth-center 响应（两服务都注册了 admin_bp）
3. 认证链：密码登录（PBKDF2/bcrypt）或 SMS/email 验证码；签发 JWT；浏览器存 `sso_token/tm_token` Cookie（HttpOnly 7 天）；`/auth/refresh` 续期；2FA 插件**可插拔（未启用不拦截）**
4. 安全基线：nginx 层限流(10r/s)、XFF 覆盖、上传目录 HTML/SVG 强制下载、未知 Host 拒绝、日志脱敏、TLS1.2/1.3 —— 这些是**安全测试的直接断言来源**
5. 首次登录可能触发 `/api/admin/first-password-set`（首密设置）流程

## 3. 测试策略

### 3.1 测试层次
1. **冒烟**（每轮先跑，~15 min）：登录→后台 dashboard→任一组 CRUD→登出
2. **功能测试**：按第 4 节各模块用例全量执行
3. **回归测试**：跨模块联动链路（见 3.3）
4. **安全测试**：参照 nginx 加固基线做对抗性用例
5. **兼容测试**：浏览器（Chrome/Edge/Firefox）、客户端类型（browser/desktop/mobile token 差异）
6. **性能抽查**：关键读接口响应时间、并发下稳定性

### 3.2 测试数据策略
- **原则**：优先用**独立测试账号**，不污染管理员主账号生产数据；测试数据加统一前缀（如 `t_`）便于清理
- **账号矩阵**：
  | 账号 | 角色 | 用途 |
  |---|---|---|
  | guxiao（已登录） | super-admin | 全功能验证 |
  | `t_user01` | 普通用户 | 用户域/越权测试 |
  | `t_admin02` | 受限管理员 | 权限隔离测试（如有权限模型） |
- 注意：当前仅 seed 了 guxiao；如需普通用户/次级管理员，先通过后台创建（属被测功能本身）
- 邮件/SMS：测试环境无真实通道 → 在 `.env` 查邮件落库（email_codes 表）或 mock 通道；验证码用 DB 内取值（见 5.2）

### 3.3 回归重点链路（跨模块）
1. **注册→登录→会话**：SMS/email 注册 → 登录 → token 刷新 → 多会话管理 → 登出
2. **内容发布→前台可见**：后台建 CMS post/block → 前台对应页面渲染正确 → 下线后不可见
3. **用户创建→权限生效**：管理员建用户/次级管理 → 新账号登录 → 操作权限边界正确
4. **品牌/媒体→多端一致**：传 logo/媒体 → 前台/后台显示一致 → 删除后前端同步
5. **配额/Key 全链路**：用户建 API key → 用 key 调接口 → 消耗配额 → 超限被拒 → key 轮换后旧 key 失效
6. **订阅/计费联动**：套餐查询 → 下单/变更 → 状态与前台 plans 一致（插件内具体逻辑另行测，核心只验入口与数据落库一致）
7. **域名配置**：后台加域名 → nginx-config 预览 → 删除，DNS/证书联动的一致性
8. **Agent 任务**：创建 agent → 绑定 prompt → 派发任务 → 任务状态流转（running/success/failed）→ 日志 → 取消/重试
9. **工作流编排**：建 workflow → 手动 run → instance 状态机(pause/resume/cancel/approve) → 节点执行日志
10. **健康守护**：停一个服务 → guardian/health 探活 → 恢复

## 6. 执行顺序与准入/准出

### 6.1 建议执行顺序
冒烟 → SEC 安全基线(P0) → AUTH → ADMIN-USERS → USER → ADMIN-SYS → CMS/CONTENT/NAV → FRO/CONSOLE → KNOWLEDGE/CLEANER/COMMENTS → AGENT → AUTO → HLTH → 跨模块回归 → 性能抽查 → 编写报告

### 6.2 准入条件（Start）
1. 核心系统部署成功，5 服务 active，DB 迁移完成
2. 管理员能登录后台
3. nginx 反代、HTTPS 自签可访问
4. 测试数据/账号已准备

### 6.3 准出条件（Exit）
1. 无未解决 **P0** 缺陷
2. **P1** 缺陷全部关闭或有明确绕行方案并评估通过
3. P0/P1 用例通过率 ≥ 100%（P0）、≥ 95%（P1）
4. 核心回归链路（3.3 十条）全部通过
5. 安全基线专项(P0)无未解决漏洞
6. 输出测试报告（含缺陷清单/统计/结论/建议）
