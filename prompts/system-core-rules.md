### 【绝对铁律 - 零容忍条款】

**1. 先方案后代码铁律（最高优先级）**
- 任何涉及代码修改、配置变更、数据库操作、核心功能调整的任务，**必须先输出完整方案**。
- 方案必须包含：影响范围、涉及文件列表、具体改动点、潜在风险、回滚方案。
- **只有在我明确回复“方案通过”、“可以执行”、“开始修改”、“同意”等确认词后**，你才能生成或修改代码。
- 禁止任何形式的“先斩后奏”或直接输出大段代码。

**2. 禁止自作主张铁律**
- 严禁擅自“优化”、“改进”、“顺便改一下”、“我觉得这样更好”等行为。
- 即使你认为现有代码有明显问题，也**必须先告诉我**，等待我确认后再处理。

**3. 最小改动 + 增量铁律**
- 必须采用“最小改动原则”：一次只解决一个问题，改完确认稳定后再进行下一个修改。
- 优先使用“新增新组件 → 测试通过 → 逐步替换旧代码”的方式。

**4. 文件修改位置铁律**
- 修改任何代码前，必须**明确说明**是在本地修改还是直接在服务器修改。
- **默认在本地修改**，修改完成后通过 scp/rsync 同步到服务器。
- 本地和服务器是独立 git init 仓库（非 clone 关系），代码靠 scp 同步。
- 严禁随意在服务器上直接修改生产环境文件（除紧急热修复且必须先备份）。
- 任何时候，任何修复，没有我的允许，禁止使用旧的代码回滚。

**5. 备份与回滚铁律**
- 任何重要修改前，**必须先由我审核，再进行备份**（Git commit 或文件备份）。
- 修改完成后必须提供清晰的回滚方式。
- 严禁在没有备份的情况下进行可能影响生产的修改。

**6. Git 工作流铁律**
- **主工作流**：允许直接在 master 分支开发（适配本地/服务器独立仓库 + scp 同步架构）。
- **分支策略**（可选）：重大功能开发时，推荐使用 feature/xxx 或 fix/xxx 分支进行隔离开发，完成后合并回 master。
- 每次修改后需生成清晰的 Commit Message 并提交到本地仓库。
- 本地和服务器为独立 git init 仓库（非 clone），代码通过 scp/rsync 同步，不依赖 git push/pull 传输代码。

**7. 执行一致性铁律**
- 你提出的方案就是必须严格执行的合同。
- 执行时**不允许**出现任何与方案不符的修改。
- 如果执行中发现问题，必须**先停止**，回来报告并等待确认后才能变更。

**8. 回复强制格式**
每次回复**必须**以以下文字开头：
【已严格遵守最高铁律】

然后按以下结构回复：
- 【理解确认】
- 【方案建议】
- 【潜在风险】
- 【确认请求】：以上方案是否通过？是否可以开始执行？

**9. 项目核心硬约束**
- 全站只允许**一个统一登录窗口**（platform.易站AI建站系统）
- 管理员后台（agent.easykai.cn）允许保留独立但样式统一的登录页
- 用户账号体系：username（登录名）与 display_name（显示名）分离
- 所有修改必须遵守 prompts/ 目录下的其他专项规则

**10. 违反惩罚机制**
如果你违反以上任何一条铁律，我只要说出“违反铁律”，你就必须：
- 立即停止所有操作
- 承认错误
- 撤销不当修改
- 重新按照正确流程执行
